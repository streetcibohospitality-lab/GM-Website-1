## Executive summary

The product has a strong security-oriented architecture and the source-level regression checks pass, but the current artifact and live infrastructure are not production-ready. Four hard blockers prevent a safe/meaningful launch: the app is pinned to the now-superseded Next.js 16.3.2 security release, all three Owner identities remain unbound, no Vercel production project exists, and the production Neon branch contains no business data.

Two additional high-severity application risks should be fixed before launch: generic command-data reads silently convert database failures into empty/zero values, and multi-stage CSV imports are not atomic and can leave partial data behind on failure.

# Release blockers — P0

## P0-01 — Current artifact is pinned to Next.js 16.3.2

**Evidence:** `package.json:24` pins `next` to `16.3.2`. `scripts/framework-gate.mjs:6-8` explicitly blocks production on versions `<=16.3.2`. At audit time, stable `16.3.3` is published.

**Impact:** The current v6.3 artifact cannot pass its own production build gate and is intentionally held behind the August security patch.

**Required action:** Upgrade to stable Next.js 16.3.3, regenerate a lockfile, install cleanly, run typecheck, static checks, production build, and browser smoke/E2E tests.

## P0-02 — Owner identities are not bound and registry is not locked

**Live result:** 3 active Owners, **0 bound Owners**. All `clerk_user_id` values are null. The runtime role still has column-level permission to update `owner_access_registry.clerk_user_id`.

**Impact:** With secure bootstrap disabled, legitimate Owners cannot enter the application. Turning bootstrap on to work around this would weaken the intended production identity model.

**Required action:** Bind the immutable Clerk user IDs for all three Owners through a controlled admin procedure, verify all 3/3, then apply the owner-registry lock so runtime can no longer bind/rebind identities.

## P0-03 — No Vercel production project exists

**Live result:** Connected Vercel team has **0 projects**.

**Impact:** There is no production deployment target, no environment-secret set, no domain binding, and no runtime log/monitoring baseline.

**Required action:** Create/link the Vercel project, set production-only Clerk/Neon/MFA/origin variables, then deploy a validated artifact and attach the production domain.

# High severity — P1

## P1-01 — Database read failures can silently become convincing zero/empty dashboards

**Evidence:** `lib/command-data.ts:31` defines a global `safe()` helper that logs query errors and returns fallback arrays/zeros. It is used across Overview, Financials, Sales, Procurement, Reports, Tasks, Documents, Alerts, and other common read paths.

**Impact:** If Neon or an individual query fails while the reporting context is otherwise considered live, the UI can show `0`, blank panels, or empty lists instead of clearly stating that data could not be loaded. In an Owner command center, a false zero is materially worse than a visible error.

**Required action:** Replace silent fallbacks on production business metrics with typed data-health/error states. Keep zero-state only for confirmed successful queries returning zero rows.

## P1-02 — Multi-stage imports are not atomic

**Evidence:** `app/api/imports/commit/route.ts` performs multiple sequential writes for several import types. Examples include period creation + financial upsert, inventory-item upsert + inventory snapshots, menu-item upsert + performance rows, and staff upsert + salary-history insert. No transaction wraps the complete import and import-job/audit record.

**Impact:** A failure halfway through can leave partially imported business data while the API returns failure and may not create a completed import-job record. Retrying could then produce a mixed state.

**Required action:** Execute each import commit as one transaction, including the business writes and import-job/audit finalization. Add rollback/fault-injection tests.

## P1-03 — No reproducible dependency lock, CI, lint, unit tests, or E2E tests

**Evidence:** The artifact contains no `package-lock.json`, `pnpm-lock.yaml`, or `yarn.lock`; no `.github/workflows`; no Playwright/Vitest/Jest config; and no ESLint config/script.

**Impact:** Transitive dependencies can change between installs; regressions are primarily guarded by regex/static scripts rather than runtime behavior; there is no automated test gate on future changes.

**Required action:** Commit a lockfile and add CI with clean install, typecheck, static audit, production build, API tests, and browser E2E flows for authentication, MFA, device registration/approval, imports, key CRUD, month close, and responsive routes.

## P1-04 — Neon production infrastructure is under-hardened

**Live findings:**

- `main` branch is **not protected**.
- Public connections are allowed (`block_public_connections=false`).
- No IP allow list is configured.
- History retention is **21,600 seconds / 6 hours**.
- Old `qa-v6-1-action-validation` branch remains online.

**Impact:** Accidental main-branch actions are easier, credential compromise has a wider network attack surface, and recovery history is short for finance/operations data.

**Required action:** Protect main, review secure connectivity options for the deployment architecture, use a least-privilege runtime credential, extend recovery/PITR policy to match business requirements, and delete or lifecycle stale QA branches after evidence is retained.

## P1-05 — Core UI text is below practical accessibility/readability size

**Static CSS result:** 384 explicit `font-size` declarations; **338 are 8px or smaller**; minimum is **4.4px**.

**Impact:** Large parts of tables, labels, filters, status metadata, and forms will be difficult to read at normal browser zoom, especially on laptops/tablets and for users with low vision. This is incompatible with a production management tool even if the aesthetic is intentional.

**Required action:** Establish a minimum readable body/metadata scale (generally materially larger than the current 4.4–8px range), test at 100%/200% zoom, and run WCAG contrast/text reflow checks.

# Medium severity — P2

## P2-01 — Keyboard activation bug on sidebar command-search control

`components/command-shell.tsx` uses a `div` with `role="button"` and `tabIndex={0}` for the sidebar shortcut but provides only `onClick`. Enter/Space does not activate it.

**Fix:** Use a native `<button>` or add correct keyboard handlers.

## P2-02 — Modal accessibility/focus management is inconsistent

The shared record modal has `role="dialog"` / `aria-modal`, but the command palette and People modal do not. No focus-trap/focus-return behavior is evident.

**Fix:** Standardize all modals on one accessible dialog primitive with labelled title, focus trap, Escape handling, focus return, and background inertness.

## P2-03 — Continuous motion has no reduced-motion path

The UI uses multiple infinite scans/pulses/tickers and animated charts, but no `prefers-reduced-motion` rule was found.

**Fix:** Add a reduced-motion media query that disables non-essential animation and auto-scrolling.

## P2-04 — Clerk session-revocation failures are silently swallowed

`lib/single-session.ts:13` and `lib/device-security.ts:26` use empty `catch {}` around Clerk session revocation.

**Impact:** The DB-side security state still provides protection, but an external revoke failure may be invisible to operators.

**Fix:** Record a high-severity security/observability event without exposing secrets.

## P2-05 — Some API error responses expose raw exception messages

Several mutation handlers return `error.message` on failure. These routes are authenticated, so exposure is limited, but database/constraint details can leak into the UI.

**Fix:** Map internal exceptions to stable user-facing error codes/messages and log detailed errors server-side.

# Security and quality strengths observed

- Exact three-Owner allowlist architecture is implemented.
- Owner registry cannot be expanded by the runtime role.
- Owner email/active fields cannot be changed by runtime.
- MFA secrets use AES-256-GCM; TOTP replay protection is implemented.
- Recovery codes are hashed.
- Approved-device cookie is HttpOnly/Secure/SameSite Strict.
- Single active session and absolute/idle session controls are implemented.
- Business-sensitive writes require recent MFA.
- Same-origin protection is present across audited mutation routes.
- Request-size limits and rate limits are broadly used.
- Closed reporting-period protections exist at both API/business-rule and database-trigger layers.
- Audit/security logs are append-only to the runtime role (no UPDATE/DELETE).
- 57 custom DB triggers are installed.
- 0 invalid indexes, 0 unready indexes, and 0 unvalidated constraints were found.
- Production demo data is disabled by default unless explicitly enabled.
- Security headers include HSTS, anti-framing, no-sniff, no-referrer, restrictive permissions policy, no-store, and noindex controls.
- Previously identified dead-action/responsive defects remain covered by the bundled 30-check interaction audit.
